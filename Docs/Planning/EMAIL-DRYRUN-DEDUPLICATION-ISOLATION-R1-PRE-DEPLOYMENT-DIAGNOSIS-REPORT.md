## 0) خلاصة تنفيذيّة

صفوف الإشعارات التي أُنشئت في وضع **المحاكاة (DryRun)** كانت تُخزَّن بنفس **مفتاح الترابط القانونيّ**
(`CorrelationKey`) الذي يستخدمه التسليم الفعليّ. وبما أنّ فحص التكرار يسبق تفرّع الوضع
(Mode branch)، ومسنودٌ بفهرس **UNIQUE** في القاعدة على العمود وحده، فإنّ كلّ صفّ محاكاة
**حَجَز مفتاح التسليم إلى الأبد**. بعد التحوّل إلى `Enabled` صارت الرسالة تُصنَّف `Duplicate`
رغم أنّها **لم تُرسَل قطّ**.

الحلّ المعتمَد (**الخيار C**) يعزل مفاتيح المحاكاة في فضاء أسماء خاصّ (بادئة `dryrun:`)،
**بلا Migration، وبلا أيّ تعديل على صفّ تاريخيّ**. الإصلاح **أماميّ فقط**: يمنع تكرار
المشكلة، ولا يفكّ حجز الرسائل المحجوزة تاريخيًّا (وهو ما تحظره التذكرة صراحةً وتُحيله
إلى تذكرة `EMAIL-MISSED-NOTIFICATIONS-RECOVERY-R1`).

## 1) السبب الجذريّ النهائيّ

**فحص تكرار أعمى عن الوضع (Mode-blind duplicate lookup) موضوع قبل تفرّع الوضع، ومسنود
بقيد تفرّد على مستوى القاعدة لا يعرف الوضع.**

بالتفصيل، ثلاثة عوامل مجتمعة أنتجت العيب — ولا يكفي أيّ منها منفردًا:

1. **مفتاح واحد للفضاءين.** `EmailNotificationService.EnqueueAsync` يبني `correlationKey`
   من (نوع الحدث + الدورة/التاريخ + المستلَم + نوع التأخّر) **دون أيّ مكوّن يدلّ على الوضع**.
   فمفتاح المحاكاة ومفتاح التسليم متطابقان حرفيًّا.
2. **ترتيب الفحص.** `AnyAsync(n => n.CorrelationKey == correlationKey)` يُنفَّذ **قبل**
   `switch` الوضع (DryRun / Enabled). فأيّ صفّ سابق — أيًّا كان وضعه أو حالته — يُنهي
   المسار بـ `ReportReminderOutcome.Duplicate` فورًا.
3. **قيد تفرّد لا يعرف الوضع.** فهرس `IX_email_notifications_CorrelationKey` على الإنتاج
   **UNIQUE btree على العمود وحده**. فحتّى لو أُصلح الفحص التطبيقيّ ليتجاهل صفوف
   المحاكاة، فإنّ محاولة إدراج صفّ التسليم بنفس المفتاح تنتهي إلى انتهاك `23505`
   ⇒ `Error` بدل الإرسال. أي أنّ القاعدة نفسها تفرض العيب.

**الحكم:** الحالة `Duplicate` كانت تعني عمليًّا «سبق أن **فُكِّر** في هذه الرسالة»، بينما
القاعدة التشغيليّة الصحيحة هي «سبق أن **سُلِّمت** هذه الرسالة». الفارق بين التفكير والتسليم
هو بالضبط ما ضاع.

## 2) مسار الكود بالضبط

```
ReportReminderSchedulerService.TickAsync(utcNow)
  └─ ReportReminderSchedulerOptions.CategoriesForHour(riyadhHour) → ReminderCategorySet
      └─ ReportReminderService.GenerateAsync(ReportReminderRunOptions)
          ├─ توليد المرشَّحين (DueEval): استحقاق دَوريّ + حارس مساواة تامّة (e.DueDate != today ⇒ تخطٍّ)
          ├─ توليد CorrelationKey لكلّ فئة:
          │    report-weekly-due:{weekKey}:{dueDate}:{userId}
          │    report-daily-due:{yyyy-MM-dd}:{userId}
          │    report-overdue:{yyyy-MM-dd|weekKey}:{userId}:{DelayType}
          │    report-review-overdue-*:{weekKey}:{userId}
          │    report-{team|department|executive}-overdue-summary:{weekKey}:{userId}
          └─ EnqueueAsync(...) → EmailNotificationService.EnqueueAsync(...)
               ├─ [1] if (Mode == Disabled) return Disabled;              ← قبل أيّ صفّ
               ├─ [2] ❌ فحص التكرار: AnyAsync(CorrelationKey == key)      ← ★ موضع العيب ★
               │        → إن وُجد: return Duplicate  (بلا أيّ نظر إلى الوضع/الحالة)
               ├─ [3] if (لا بريد للمستلَم) → صفّ Skipped + SkippedNoEmail
               ├─ [4] بناء الكيان EmailNotification { Mode = _options.Mode, CorrelationKey = key }
               ├─ [5] if (Mode == DryRun) { Status = DryRun; SaveChanges; return Created; }  ← لا إرسال
               └─ [6] وإلّا: إرسال فعليّ عبر IEmailSender ثمّ Status = Sent / Failed
```

**نقطة الانكسار:** الخطوة **[2]** تسبق الخطوتين **[5]** و**[6]**. الصفّ الناتج عن [5]
(محاكاة، `Status = DryRun`، `SentAt = null`) يبقى في الجدول حاملًا المفتاح القانونيّ،
فيُطلق [2] في كلّ تشغيل لاحق — بما فيها كلّ تشغيلات ما بعد التحوّل إلى `Enabled`.

**سلوك ما بعد إعادة التشغيل (Restart):** الحجز في القاعدة لا في الذاكرة ⇒ إعادة التشغيل
لا تُحرِّره. (وهذا مقصود ومطلوب لصفوف `Sent`، وخاطئ لصفوف `DryRun`.)

**سلوك الاستطلاع كلّ 15 دقيقة (`PollMinutes=15`):** المرشَّح يُعاد توليده في كلّ استطلاع
داخل النافذة، ويُصنَّف `Duplicate` في كلّ مرّة — بلا حدّ، وبلا أيّ أثر جانبيّ. أي أنّ
الرسالة **تظلّ محجوزة إلى الأبد**، لا مؤجَّلة.

**`email_outbox` (القناة القديمة):** **غير مفحوصة إطلاقًا** في هذا المسار، وهي 0 صفّ على
الإنتاج. لا علاقة لها بالعيب ولم تُمَسّ.

## 3) سلوك التفرّد على مستوى القاعدة

| الطبقة | الآلية | الحالة قبل الإصلاح |
|---|---|---|
| التطبيق | `AnyAsync(CorrelationKey == key)` قبل تفرّع الوضع | أعمى عن الوضع |
| القاعدة (Production) | `IX_email_notifications_CorrelationKey` — **UNIQUE btree على العمود وحده** | أعمى عن الوضع |

**الحالات التي كانت تحجز المفتاح فعليًّا:** **كلّها بلا استثناء** —
`Pending`, `DryRun`, `Sent`, `Failed`, `Skipped`, `Cancelled`.
لا تمييز بين «محاكاة» و«تسليم»، ولا بين «نجح» و«فشل».

> **ملاحظة توثيقيّة مهمّة:** `EmailNotificationMode` و`EmailNotificationStatus` مُخزَّنان
> **نصًّا (varchar)** في PostgreSQL. أيّ استعلام تشخيصيّ يقارنهما بأعداد صحيحة يُرجِع صفرًا
> مضلِّلًا. كلّ قياسات هذا التقرير أُجريت بمقارنة نصّية.

**الخيار (A) مرفوض:** يغيّر شكل مفاتيح التسليم التاريخيّة الـ28، فتفقد قدرتها على الحجز،
فتُعاد رسائل سبق إرسالها فعليًّا إلى موظّفين حقيقيّين.

**الخيار (B) مرفوض:** بلا Migration ينتهي إلى انتهاك `23505` (الفهرس الفريد ما زال على
العمود وحده) ⇒ `Error` لا إرسال. ومع Migration يفكّ حجز الرسائل التاريخيّة **تلقائيًّا
عند أوّل استطلاع** — وهو إرسال جماعيّ غير مصرّح به يخالف نصّ التذكرة.

**الخيار (C) معتمَد.** عزل **غير متماثل**: صفوف المحاكاة وحدها تُخزَّن بمفتاح مسبوق
بـ`dryrun:`؛ ومفاتيح `Enabled` تبقى قانونيّة حرفيًّا. النتيجة:

- محاكاة جديدة **لا** تحجز مفتاح تسليم ⇒ العيب لا يتكرّر.
- صفوف `Enabled/Sent` تبقى حاجزة تمامًا ⇒ لا إرسال مكرّر.
- صفوف المحاكاة التاريخيّة تبقى بمفاتيحها القانونيّة ⇒ **تبقى حاجزة**، وهو ما تفرضه
  التذكرة (ممنوع الإرسال هنا، وممنوع تعديل المفاتيح التاريخيّة).
- **بلا Migration**، والتراجع = حذف سطر بناء `effectiveCorrelationKey`.

**فائدة إضافيّة للتعافي:** بعد نشر (C)، تصبح آليّة التعافي في التذكرة المنفصلة عمليّة
`UPDATE` واحدة محكومة (وضع بادئة `dryrun:` على صفوف المحاكاة التاريخيّة المستحقّة)
**بلا أيّ تغيير في الكود** — كلّ رسالة ما زالت مستحقّة تُطلَق، وما لم يعد مستحقًّا لا يُطلَق
لأنّ حارس الاستحقاق يسبق.
