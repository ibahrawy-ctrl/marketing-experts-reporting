6. **حقول ميّتة**: `decisions_needed` = 0%، `conv_rate` = 37%.

9. **لا سير عمل توصيات الكريتف** (من فرق المحتوى/التصميم/الفيديو/SEO) إطلاقًا.

مسار مقترح لفرص الترويج الإبداعيّ القادمة من فرق المحتوى/التصميم/الفيديو/SEO:

```
اقتراح مُنشئ (Content/Design/Video/SEO)
   → مراجعة Team Leader
      → إظهار لـ Account Manager (رؤية)
         → تقييم Media Buyer
            → [يحتاج تحسين] ⟲ يعود للمُنشئ
            → [مرفوض] ✗ يُغلق بسبب
            → [مقبول للاختبار] → مجدوَل → Live → تُسجَّل النتيجة → مُغلق
```

**قاعدة الاحتساب:** التوصية **لا تُحتسَب حملة/نتيجة/Live** إلا بعد **الموافقة + الإطلاق الفعليّ**. قبلها = مقترح في قائمة الانتظار (Pipeline) لا إنجاز. تُخزَّن حالة كل توصية (`Proposed/TLReviewed/AMVisible/MBAssessing/NeedsEnhancement/Rejected/ApprovedForTest/Scheduled/Live/ResultRecorded/Closed`).

**تنبيه نطاق:** ربط هذا السير بفرق أخرى (المحتوى/التصميم…) قد يتطلّب Backend/كيان جديد ⇒ يميل بالخيار نحو C (القسم 16). يمكن في مرحلة أولى تمثيله كقسم داخل قالب الـMedia Buyer (بلا كيان مشترك) ثم ترقيته لاحقًا.

## 11) مراجعة UX (الحالي)

**مستوى الإثبات:** UX الحالي رُوجِع **من الكود (`SubmissionsPage.tsx` — عرض/تحرير القسم المتكرّر والشبكات) ومن بنية البيانات الفعلية**. **لم تُلتقَط لقطات مُصادَقة على الإنتاج** لعدم توفّر حسابات مستخدمين حقيقية ولالتزام عدم إعادة تعيين أيّ كلمة مرور دون موافقة جديدة (نفس مبدأ MODERATION-UX-R1). هذا قيد موثَّق لا عيب تشخيصيّ.

**ملاحظات UX الحالية:**
- القسم المتكرّر يعرض كل مشروع كبطاقة، لكن **الشبكة الداخلية `campaigns_grid` تُدخَل كخلايا نصّية** ⇒ تجربة إدخال هشّة (لا تحقّق نوع، لا قوائم منسدلة للحالة/المنصّة).
- **لا فصل بصريّ** بين حالة الحملة والنتيجة والعمل — كلّها نصّ.
- لا مؤشّر «Live مقابل تحضيريّ» ⇒ القارئ (TL/AM/المدير) لا يميّز الإنجاز الفعليّ.

## 16) خيارات التنفيذ

**الخيار A — UX فقط فوق سكيمة V5 الحالية (Frontend فقط):**
تحسين العرض/الإدخال (Accordion، بطاقات، قوائم منسدلة على مستوى الواجهة) دون تغيير السكيمة/الإصدار. **مزايا:** أسرع، بلا Migration، بلا Backend، توافق خلفي كامل. **عيوب:** **لا يحلّ التجميع** (المفاتيح فارغة والأرقام نصوص عند التخزين تبقى)، ولا دورة حياة مفروضة، ولا فصل حقيقي — تجميل فوق أساس هشّ.

**الخيار B — إصدار قالب جديد V6 مُهيكَل، بلا Backend جديد:**
إصدار V6 (مفاتيح ثابتة + أنواع أعمدة + Select للحالة/المنصّة/المقياس + دورة حياة + أقسام مفصولة + أفضل/أضعف) عبر `TemplateSeeder`. **مزايا:** يحلّ التجميع والفصل ودورة الحياة، توافق خلفي كامل (V5 محفوظ)، **بلا كيان/جدول جديد** (يعيد استخدام ProjectRepeatableSection + Grid الموجودَين). **عيوب:** توصيات الكريتف عبر الفرق تبقى قسمًا داخليًّا (بلا ربط كيانيّ حقيقيّ بفرق أخرى)، والتجميع يبقى على مستوى العرض (قراءة JSON) لا استعلام مُفهرَس.

**الخيار C — V6 + تحسينات Backend/تجميع خفيفة:**
كل B + طبقة تجميع خادمية تقرأ حقول V6 المُهيكَلة وتوفّر مؤشّرات جاهزة للوحات (TL/Project/AM/المدير) مع احترام قاعدة «Live فقط»، و(اختياريًّا) كيان توصيات كريتف مشترك بين الفرق. **مزايا:** أعلى قيمة (تجميع آليّ حقيقيّ + سير كريتف عبر الفرق). **عيوب:** أكبر سطحًا؛ قد يتطلّب Migration واحدة لو أُضيف كيان الكريتف؛ يحتاج حسم قرارات وظيفية أولًا.

## 22) تصحيح الغموض في التقرير القديم

1. **تعريف «النتيجة» حسب هدف الحملة:** يُضاف عمود `result_metric` (Select: `Leads/Purchases/DirectionClicks/Impressions/Clicks/Messages/Reach`). قيمة النتيجة `result_value` تُفسَّر وتُجمَّع **حسب المقياس فقط** (لا جمع Leads مع نقرات اتجاه). يزيل التحميل الدلاليّ المكتشَف في W28/W29.
2. **إزالة تكرار الصرف:** يُدمَج L6 «إجمالي الصرف» وL11 «الإنفاق الإعلاني» في حقل واحد `spend_total` (Currency). الصرف على مستوى الحملة في الشبكة، والإجمالي مُشتَقّ.
3. **ربط أفضل/أضعف حملة بحملة فعلية:** `best_campaign_ref` / `weakest_campaign_ref` = مرجع إلى صفّ في شبكة الحملات (بالاسم المُدخَل ضمن الشبكة، لا نصّ منفصل) + سبب. يمنع «أفضل حملة» غير الموجودة أصلًا في السجل.
4. **تحويل أسباب المشكلات إلى مفردات مضبوطة:** `root_cause` (Select 9 قيَم من L15) بدل النصّ الحرّ `issue_cause`، مع `root_cause_note` اختياريّ للتفصيل.
5. **تحويل طلبات الفرق/الاختبارات/القرارات إلى جداول قابلة للمتابعة والتجميع:** L16–L23 تصبح **TableGrid** بأعمدة حالة/أولوية مضبوطة ⇒ قابلة للفرز والتجميع والمتابعة عبر الأسابيع.
6. **تصحيح وحدات KPI:** «إجمالي النتائج» = Number (لا ر.س)؛ «متوسط تكلفة النتيجة» = Currency محسوبة (لا %).

## 27) Conditional Rules (قواعد شرطيّة)

1. **بوّابة الاحتساب:** حملة تدخل مؤشّرات Live/الإنجاز **فقط** إذا `lifecycle_status ∈ {Live,Paused,Optimizing,Completed}`. غيرها = Pipeline لا نتيجة.
2. **اشتقاق التكلفة:** `avg_cost_per_result = spend_total / results_total` حين `results_total>0`، وإلا «—».
3. **تجميع النتيجة:** تُجمَّع `result_value` **فقط ضمن نفس `result_metric`** (لا خلط).
4. **التصعيد يُلزِم إجراءً:** `needs_escalation=true` ⇒ يُطلَب صفّ واحد على الأقل في `escalations[]`.
5. **أفضل/أضعف حملة تشير لموجود:** `best/weakest_campaign_ref` يجب أن يطابق `campaign_name` مُدخَلًا في `campaigns[]`.
6. **صحّة النِّسَب:** حقول Percentage (CTR/Conv/time) ضمن 0–100.
7. **الطلبات والقرارات المفتوحة تُرحَّل بصريًّا** للأسبوع التالي (تذكير UX، بلا كتابة آليّة).

- `TrackingUnavailable` ⇒ يُلزَم `camp_note` بسبب تعذّر التتبّع؛ تُستثنى من CPR والإجماليات وتُعدّ خطرًا في `mb_kpi_risks`.

**منع رقم بلا نوع:** لا يُقبَل `camp_result_value` بدون `camp_result_metric` عند Submit.

## 40) القسم الرابع (تكملة) — دورة حياة الحملة (القرار 2)

13 حالة مضبوطة، مقسّمة إلى 5 مجموعات مستقلّة الاحتساب:

| Group | States | التعريف الموجز |
|---|---|---|
| Preparation | Draft, AwaitingAssets, UnderPreparation, UnderReview | قيد التجهيز داخليًّا |
| Waiting | WaitingClientApproval | بانتظار موافقة العميل |
| Ready | ReadyToLaunch, Scheduled | مكتملة، تنتظر/مجدولة الإطلاق |
| Live | Live, Optimizing, Paused | فعّالة أو متوقّفة مؤقتًا بلقطة أداء |
| Historical | Completed | منتهية بنتيجة نهائية |
| Blocked | Blocked, Cancelled | محجوبة/ملغاة |

**قواعد العدّادات المستقلّة (لا بوابة واحدة):**
- `Live Campaign Count` = عدّ `{Live, Optimizing}` (Paused تُعرض منفصلة كـ«متوقّفة»).
- `Ready Count` = عدّ `{ReadyToLaunch, Scheduled}`.
- `Waiting Client Count` = عدّ `{WaitingClientApproval}`.
- `Blocked Count` = عدّ `{Blocked, Cancelled}`.
- `Historical Campaign Count` = عدّ `{Completed}`.
- `Actual Performance Totals` (صرف/نتائج/CPR) = تُحتسَب فقط من `{Live, Optimizing, Paused, Completed}` **ولها نتيجة/صرف موثّق**، مستقلّة تمامًا عن العدّادات أعلاه.

انتقالات نموذجية: Draft→AwaitingAssets→UnderPreparation→UnderReview→WaitingClientApproval→ReadyToLaunch→Scheduled→Live↔Optimizing↔Paused→Completed؛ Blocked/Cancelled من أي حالة.

## 51) القسم الخامس عشر — Backward Compatibility (V1→V6 بلا كسر)

- V6 = **إصدار جديد منشور** داخل قالب Growth `16d07519`. V1–V5 وتسليماتها تبقى كما هي **بلا ترحيل بيانات ولا ترحيل مسودّات**.
- العارض يقرأ `ReportSubmission.ReportTemplateVersionId` ⇒ يعرض **سكيمة نسخة ذلك التسليم**. تسليم W28/W29 (V5) يُفتح بسكيمة V5 (مشاريع نصّية) بلا خطأ.
- الحقول الجديدة في V6 (دورة الحياة/الفانل الموسّع/الكريتف…) **غير موجودة** في سكيمة V5 ⇒ لا تظهر للقديم ⇒ **صفر فقدان حقول** (نفس مبدأ `moderationGroups→null` = تخطيط مسطّح للقديم).
- طبقة التجميع تقرأ فقط تسليمات نسخة V6 (تُميَّز بـ`VersionNumber`/مفاتيح V6)؛ التسليمات القديمة تبقى مقروءة تاريخيًّا دون دخولها تجميع V6 المهيكَل.
- الإسناد: V6 يرث إسناد قالب Growth تلقائيًّا بكونه أحدث نسخة منشورة؛ القالب by-client `05061575` **يُلغى إسناده** (لا يُحذف) لتفادي الازدواج.

## 55) القسم التاسع عشر — UAT Scenarios

1. **دورة حياة كاملة:** موظّف ينشئ مسودة V6 → مشروعان → حملات بحالات مختلفة → حفظ حرّ → إرسال → المراجع يعتمد → Closed → Read-Only.
2. **بوابة الشبكة:** `activity_state=NoCampaignsThisPeriod` ⇒ الشبكة مخفية، سبب إلزاميّ، الإرسال ينجح بلا حملات.
3. **تعريف النتيجة:** حملة Objective=Leads ⇒ result_metric مقيّد بـLeads؛ إدخال value بلا metric ⇒ رفض عند Submit.
4. **حالات النتيجة:** HasResults يُلزم القيمة؛ NoResultsYet لا يُلزم ولا يدخل الإجمالي؛ TrackingUnavailable يُلزم الملاحظة ويظهر كخطر.
5. **العدّادات المستقلّة:** خليط حالات ⇒ Live/Ready/Waiting/Blocked/Historical كلها صحيحة ومنفصلة، والإجماليات الأدائية من الحيّة/المنتهية فقط.
6. **أفضل/أضعف حملة:** يظهر فقط حين ≥2 مؤهّلة؛ الاختيار من الشبكة فقط؛ مرجع لحملة غير موجودة ⇒ رفض.
7. **الفانل:** results_status=🔴 ⇒ الفانل إلزاميّ؛ عدّة أسباب Confirmed/Suspected + فريق مسؤول + إجراء + أولوية + حالة.
8. **الكريتف:** أفضل/أضعف كريتف بحقوله؛ فرصة ترقية مستقلّة بلا تكرار الإدخال؛ ربط الحملة يعمل.
9. **القواعد الشرطية:** كل R1–R18 تُختبَر (تظهر/تُلزَم في حالتها فقط، Draft حرّ).
10. **التجميع:** لوحات TL/Project/AM/Exec تقرأ القيم الصحيحة بمفتاح projectId؛ النتائج مجمَّعة لكل metric على حدة.
11. **التوافق الخلفيّ:** تسليم V5 قديم يُفتح بسكيمته (مشاريع نصّية) بلا حقول V6 وبلا خطأ.
12. **Mobile/RTL:** الشبكات تتحوّل لبطاقات، KPI `grid-cols-2`، Accordion كامل، Sticky header.
