## المُخرَج (1) — معمارية الحالة الراهنة (المسار الكامل لعرض التقرير)

**المسار end-to-end الذي يبني صفحة عرض التقرير:**

```
GET /api/submissions/{id}
  → SubmissionsController (Reporting.Api)
  → SubmissionService.GetAsync → BuildDtoAsync   [SubmissionService.cs:732]
       • يقرأ ReportSubmission + FieldValues + ApprovalSteps
       • يقرأ TemplateFields للنسخة، مرتّبة بـ f.Order      [:745-749]
       • يبني SubmissionFieldValueDto لكل حقل (تمرير خام)  [:751-757]
  → SubmissionDto { FieldValues[], ApprovalSteps[], ClientId?, ProjectId?, … }
  → (الواجهة) SubmissionsPage.tsx / SubmissionDetail       [:709]
       • تصنيف الحقول: prsFields / scorecardFields / overviewFields  [:820-828]
       • renderPRS  → ProjectRepeatableDisplay              [:831-852 → :1584]
       • renderField (نظرة عامة + Scorecard)                 [:855-950]
```

**حقائق معمارية مثبَتة:**

- **الـ Backend عديم الوعي بالعرض (presentation-agnostic).** `BuildDtoAsync` تمرير خام بحت: لكل حقل تُعاد `(TemplateFieldId, Label, FieldType, ValueText, ValueNumber, ValueDate, ValueBool, ValueJson, IsRequired, HelpText, ConfigJson)` — [`SubmissionModels.cs:5-16`]. **لا تصنيف، لا ميتاداتا عرض، لا حقول محسوبة، لا شارات، لا أولوية.** الترتيب الوحيد = `f.Order` [`SubmissionService.cs:747`].
- **كل قرارات التخطيط في الواجهة.** لا يوجد أي DTO عرضٍ مخصّص للأدوار على الخادم.
- **يوجد بالفعل مُصيّر «Project-first».** الواجهة الحالية ليست مسطّحة بالكامل — عند وجود PRS تعرض: (أ) «نظرة عامة» (overviewFields)، (ب) Scorecard رقمي مطويّ، (ج) جسم المشاريع [`:1064-1099`]. لكن **جودة عرض جسم المشاريع تعتمد كليًّا على مطابقة مفردات المودريشن** (انظر المُخرَج 4).
- **مُصيّر `ProjectRepeatableDisplay` له تخطيطان** [`:1584`]:
  - **مسطّح** (`!groups`) [`:1611-1630`]: `<dl>` من `dt/dd` **متساوية الوزن** لكل حقل فرعي، والقيمة الفارغة ⇐ «—» عبر `showAnswer` [`:1599-1603`].
  - **مجمّع فاخر** (`groups`) [`:1633-1668`]: أكورديون + بطاقات KPI (`PrsKpiCards`) + مجموعات معنونة + جداول Grid مطويّة + ترويسة غنيّة بشارات (`PrsProjectHeader`).
  - القرار بينهما تصنعه `moderationGroups(fields)` [`:645-662`]: تُرجِع `null` (⇒ مسطّح) إلا إذا طابق حقلٌ **مفاتيح مفردات المودريشن** المثبّتة `MOD_GROUP_DEFS` [`:624-630`].

## المُخرَج (4) — الجذر الدقيق لمشكلة المخرَج (Root Cause)

**ليست مشكلة بيانات ولا مشكلة خادم — بل مشكلة مُصيّر عامّ + غياب ميفولة عرض.** التفصيل الدقيق:

1. **الخادم يمرّر البيانات خامًّا بلا أي دلالة عرض** [`SubmissionService.cs:751-757`, `SubmissionModels.cs:5-16`]. لا يوجد أي مكان يقول «هذا الحقل شارة»، «هذا مقياس»، «هذا قرار إداريّ بارز».
2. **المُصيّر الفاخر (بطاقات KPI + مجموعات + شارات + جداول) مقيَّد حصريًّا بمفردات المودريشن.** `moderationGroups` [`:645-662`] تعتمد على مفاتيح `MOD_GROUP_DEFS` [`:624-630`] = (`project_status`, `time_consumption`, `incoming_messages`, `answered_messages`, `avg_response_minutes`, `problematic_comments`, `escalations`, `complaints`, `converted_opportunities`, `cases_grid`, `done`, `issues`, `recurring_questions`, `next_week`, `recommendations`). و`PrsKpiCards` [`:665-690`] تعتمد على `MOD_KPI_CARDS` [`:633-641`] بنفس المفاتيح.
3. **مفاتيح تقرير إدارة الحسابات لا تطابق هذه المفردات** (عدا `project_status` صدفةً). لذا:
   - `PrsKpiCards` تُرجِع `null` (لا مفتاح من `deliverables_*` ضمن `MOD_KPI_CARDS`) ⇒ **لا بطاقات مقاييس** رغم وجود 3 حقول رقمية مثاليّة لذلك.
   - حتى لو دخل التخطيط المجمّع، فمجموعة «📋 نظرة عامة» تحوي `project_status` فقط، وكل الـ17 حقلًا الباقية تُقذَف في مجموعة ذيليّة «📄 حقول إضافية» **كصفوف dt/dd متساوية الوزن** [`:1646-1653`] — أي نفس المشكلة.
   - المُخرَج الإنتاجي الفعلي [جديد ص.1–2] يُظهِر **التخطيط المسطّح** [`:1611-1630`]: بطاقة لكل مشروع بعنوان بسيط + `<dl>` من 18 صفًّا متطابق الشكل، القيم الفارغة «—».
4. **الأنواع البنيويّة موجودة لكنها لا تُترجَم بصريًّا:** `Select` (status/risk/relationship) يُعرض كنصّ لا كشارة؛ `Number` (deliverables) يُعرض كصفّ لا كمقياس/مصفوفة؛ `client_relationship`/`risk_severity` لا تُلوَّن؛ `decisions_required` لا يُبرَز.
5. **العناصر متعدّدة العناصر (طلبات/قضايا/تأخيرات) نصّ حرّ LongText مفرد** ⇒ لا يمكن للمُصيّر عرضها كجدول لأن المُدخَل نفسه فقرة واحدة (هذا حدّ إدخاليّ لا عرضيّ — يخصّ الخيار C).

**الحكم:** ٨٠٪ من المشكلة **قابلة للحلّ في الواجهة فقط** (Option A) عبر مُصيّر واعٍ بالأنواع + ميفولة عرض؛ و٢٠٪ (جداول العناصر المتعدّدة، جدول تخصّصات cross-functional) تتطلّب إمّا Read Model للعرض (Option B) أو تعديل مخطّط إدخال (Option C).

## المُخرَج (5) — مصفوفة قرار الإدخال مقابل الإخراج لكل حقل (Phase 3)

**القاعدة المُلزِمة:** لا نُجبِر مدير الحساب على **إعادة إدخال** بيانات يملكها Media Buyer أو Moderator أو تخصّص آخر. ما يملكه غيره ⇐ **يُقرأ ويُعرَض** في تقرير AM (اشتقاق)، لا يُدخَل.

## المُخرَج (10) — الخيارات A/B/C + التوصية (Phase 7)

### الخيار A — واجهة فقط (Frontend-only, KPI-Safe)
مُصيّر واعٍ بالأنواع + ميفولة عرض في الواجهة: شارات RAG لكل Select، بطاقات مقياس للأرقام، إخفاء الفارغ، إبراز القرارات، ملخّص محفظة + جدول فهرس + تبويب مشاريع.
- **التغيير:** `SubmissionsPage.tsx` (المُصيّرات) فقط. **بلا Backend، بلا Migration، بلا مساس بـ ValueNumber/KPI.**
- **يعالج:** G1–G5, G10 (٨٠٪ من الشكوى).
- **لا يعالج:** G6 (جداول العناصر المتعدّدة تتطلّب إدخالًا مجدولًا)، G7/G8 (اللوحة المشتركة).
- **المخاطرة:** منخفضة جدًّا. **قابل للاسترجاع فورًا** (استعادة bundle).

### الخيار B — Read Model للعرض/اللوحة (Backend, بلا كتابة)
DTO عرض مخصّص + Endpoint قراءة `GET /api/projects/{id}/cross-functional?period=` يجمع تقارير التخصّصات على `projectId` ويشتقّ جدول حالة التخصّصات واللوحة المشتركة.
- **التغيير:** خدمة قراءة + Controller + DTO + صفحة لوحة. **بلا Migration** (قراءة فقط من الجداول القائمة).
- **يعالج:** G7, G8 (الرؤية المشتركة، جدول التخصّصات المشتقّ).
- **المخاطرة:** متوسطة (منطق تجميع، أداء الاستعلام) — لكن قراءة فقط ⇒ لا خطر بيانات.

### الخيار C — إدخال مشروع مُهيكَل (Template Version Bump)
تحويل `client_requests`/`open_issues`/`delays` من LongText إلى Grid داخل PRS (نسخة قالب جديدة).
- **التغيير:** ConfigJson لنسخة قالب جديدة + محرّر Grid (قائم أصلًا في الواجهة). **بلا Migration سكيمة** (يبقى ValueJson)، لكن **يتطلّب bump نسخة القالب** والتقارير القديمة تبقى على نسختها (Versioning).
- **يعالج:** G6.
- **المخاطرة:** متوسطة (تدريب المستخدمين، توافق النسخ) — يجب ألّا يمسّ `ValueNumber` الذي يقرؤه KPI بالاسم.

### التوصية — تنفيذ مرحليّ A → B → C
1. **المرحلة 1 (A):** المُصيّر الواعي بالأنواع — أعلى قيمة، أقلّ مخاطرة، يحلّ جوهر شكوى «القراءة التنفيذيّة». تُنشَر أولًا وتُثبَّت.
2. **المرحلة 2 (B):** Read Model + اللوحة المشتركة — الرؤية 360 وجدول التخصّصات المشتقّ.
3. **المرحلة 3 (C):** جدولة العناصر المتعدّدة — بعد استقرار A/B وبقرار منتَج صريح (bump نسخة).

**السبب:** A مستقلّ وقابل للاسترجاع ويحلّ الأغلب دون أي خطر خادم/بيانات؛ B يبني فوق روابط projectId المثبتة دون Migration؛ C آخِرًا لأنه يمسّ الإدخال ويتطلّب نسخ قالب وتدريبًا.
