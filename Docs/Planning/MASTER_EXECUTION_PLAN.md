## المبدأ الحاكم للخطة (Governing Principle)

هذه الخطة **تحافظ على تسلسل الأولويات والإنتاج المعتمَد** ولا تُعيد ترتيبه أو تُلغيه أو تُوسِّعه لمجرّد أنّ رؤية BRD طويلة المدى أوسع. تُميِّز الخطة بصرامة بين سبع فئات:

| # | الفئة | المعالجة في الخطة |
|---|-------|-------------------|
| 1 | نطاق الإنتاج الحالي (Current Production Scope) | HORIZON A — يُحمى ولا يُمَسّ إلا بإصلاح |
| 2 | أعمال الاستقرار الحالية (Current Stabilization) | HORIZON A |
| 3 | عمل قيد التطوير (Under Development) | HORIZON A/B (حسب النضج) |
| 4 | عمل تالٍ معتمَد (Approved Next) | HORIZON B |
| 5 | عمل مؤجَّل (Deferred) | HORIZON C — يبقى مؤجَّلًا |
| 6 | رؤية BRD طويلة المدى (Long-term Vision) | HORIZON C |
| 7 | توصيات معمارية اختيارية (Optional Recommendations) | مُعلَّمة صراحةً كتوصية في كل موضع |

**قاعدة إعادة الترتيب:** أي اقتراح لإعادة ترتيب الأولويات يوضَع حصريًّا في قسم «تغيير أولوية مُقترَح — يتطلّب موافقة المالك» في نهاية الوثيقة، ولا يُطبَّق ذاتيًّا.

## HORIZON A — استقرار الإنتاج الحالي (Current Production Stabilization)

**الهدف:** تثبيت ما هو مبنيّ فعلًا وحمايته، وسدّ العيوب المعروفة، واستكمال نطاق التقارير الحالي — **دون** إدخال وحدات مؤسسية كبرى.

### A.1 — نطاق HORIZON A (حصريًّا)
1. **حماية الإنتاج:** لا تغيير غير مُصرَّح؛ كل نشر بنسخة معزولة + Backup + تحقّق ما بعد النشر (AD-110).
2. **سدّ العيوب المعروفة:** CSP (R1)؛ لا عيوب Critical/High أخرى مؤكَّدة.
3. **تأمين العمل قيد التنفيذ:** إيداع عمل `develop` غير المُودَع (R2/AD-10) قبل أي بناء فوقه.
4. **تصليب بيئة الاختبار:** عزل قاعدة اختبارات التكامل المشتركة (R8/AD-109) + تقوية تغطية اختبارات النطاق/الصلاحيات (R6/AD-103 — تغطية اختبارية الآن، لا إعادة معمارية).
5. **استكمال نطاق التقارير الحالي:** ضمن حدود القوالب/التجميع/اللوحات القائمة فقط.

### A.2 — خارج نطاق HORIZON A (Out of Scope)
- Workflow Engine (P3+) · Files Service (P4) · Task Platform (P5) · CRM B2B (P6) · Governance/CAPA (P7) · Reporting Intelligence/BI (P8) · Integrations/AI (P9).
- أي إعادة هيكلة معمارية كبرى (Permission Service الموحّد، Read Models، Event Bus) — تبقى **توصيات** لأفق C.

1. **بوّابة أفق:** لا انتقال A→B قبل استيفاء معايير خروج A؛ ولا B→C قبل قرار مالك.

## القسم 4 — سياسة البيئات والنشر المعتمَدة (Environments & Deployment Policy) — تاسعًا

> **قرار معماريّ وتشغيليّ رسميّ مُعتمَد من المالك.** يحكم هذا القسم كيفية استخدام بيئتَي **TEST** و**RC** ومسارات النشر، ويُرجَع إليه من `ARCHITECTURAL_DECISION_REGISTER.md` (AD-114) ومن `HOTFIX_FORWARD_INTEGRATION_REGISTER.md`. **هذا القسم توثيقيّ فقط — لا يُنشئ بيئة ولا Release ولا يبدأ أي نشر.**

### 4.1 — مساران منفصلان تمامًا (Two Fully Separated Tracks)

| البُعد | **المسار 1 — التوسّع المؤسسي (Enterprise Expansion)** | **المسار 2 — الإصلاحات العاجلة/السريعة (Urgent/Fast Fixes)** |
|--------|------------------------------------------------------|-------------------------------------------------------------|
| **البيئة** | **TEST** = Staging مخصّص لبناء/تجميع/اختبار التوسّعة كمرحلة كاملة متكاملة | **RC** = Release Candidate لاختبار Hotfixes والإصلاحات المحدودة/السريعة المبنية على أساس الإنتاج الحالي |
| **الغرض** | التوسّعة الكبرى وفق BRD/الخطة المعتمَدة (إدارة العملاء/المشاريع، Workstreams، Deliverables، Project-First Execution، التخطيط/التنفيذ، ومراحل مؤسسية لاحقة بالترتيب المعتمَد) | إصلاح مرتبط بالإنتاج الحالي (Hotfix عاجل، إصلاح علّة محدود، تغيير سريع منخفض النطاق، تحليل/تحقّق تشغيليّ، مرشّح إصدار قريب من الإنتاج الحالي، Regression للإصلاح المحدود) |
| **خطّ الإصدار** | Develop/Expansion → إكمال كل مكوّنات المرحلة → **TEST** كمرحلة متكاملة → QA/UAT/Regression → الإنتاج `reports` | أساس الإنتاج الموثَّق → عزل Hotfix → Build+اختبار آمن → **RC** → تحقّق+اعتماد → الإنتاج `reports` |
| **UAT** | على نسخة **TEST** مثبّتة (pinned) بعد نشر المرحلة الكاملة/الحزمة المتكاملة المستقرّة | على **RC** فقط، محصورة بالسيناريو المتأثّر بالإصلاح |

**قاعدة الفصل المُلزِمة:** لا يُخلَط المساران ولا يُستبدَل أحدهما بالآخر إطلاقًا.

### 4.2 — وظيفة TEST (Staging للتوسّعة الكبرى)
- TEST **ليست** لإصلاحات الـHotfix اليومية؛ هي حصرًا للتوسّعة الكبرى وفق BRD/الخطة المعتمَدة.
- تُجمَّع التوسّعة تدريجيًّا على TEST، لكنها **لا** تُعامَل كنسخة موازية لكل إصدار/Hotfix إنتاجيّ.
- **قاعدة صريحة:** الـHotfixes **لا** تُنشَر فرديًّا إلى TEST؛ تبقى TEST مستقلّة حتى تجهز المرحلة الكبرى للاختبار المتكامل كحزمة واحدة.
- **المسار:** التطوير (التوسّعة) → نشر المرحلة الكاملة إلى TEST → اختبار تكامل/QA → UAT على TEST → إصلاح ملاحظات التوسّعة → Regression شامل → اعتماد الإصدار → الإنتاج `reports`.
- **التوسّعة الكبرى لا تمرّ عبر RC إطلاقًا.**

### 4.3 — وظيفة RC (بيئة الإصلاحات المرتبطة بالإنتاج الحالي)
- RC لإصلاحات مرتبطة بالإنتاج الحالي فقط (Hotfix عاجل، إصلاح علّة محدود، تغيير سريع منخفض النطاق، تحليل/تحقّق تشغيليّ، مرشّح إصدار قريب من الإنتاج، Regression للإصلاح المحدود).
- **المسار:** أساس الإنتاج الموثَّق → عزل Hotfix → Build+اختبار آمن → RC → تحقّق+اعتماد → الإنتاج `reports`.
- **RC ليست بيئة التوسّعة المؤسسية.**

### 4.4 — Hotfixes أثناء تطوير التوسّعة (Forward-Merge إلزاميّ)
عند ظهور Hotfix أثناء تطوير التوسّعة يُتَّبع التسلسل التالي **إلزاميًّا**:
1. البناء من نسخة الإنتاج الموثَّقة.
2. الاختبار على RC.
3. النشر إلى الإنتاج بعد الاعتماد.
4. **دمج كوده في خطّ تطوير التوسّعة (Forward-Merge إلزاميّ).**
5. إضافة اختبارات Regression الخاصة به إلى التوسّعة.
6. ضمان احتواء التوسّعة النهائية على الإصلاح قبل أي إصدار مستقبليّ.

> **مهم:** الدمج الأماميّ (Forward-Merge) في كود التوسّعة **إلزاميّ**؛ النشر الفرديّ للـHotfix إلى TEST **غير مطلوب**؛ لكن ظهوره لاحقًا **ضمن التوسّعة الكاملة** على TEST **إلزاميّ** عند نشر المرحلة الكاملة.

### 4.5 — منع خلط خطوط الإصدار (No Mixing Release Lines)
| خطّ الإنتاج/Hotfix | خطّ التوسّعة |
|--------------------|--------------|
| أساس الإنتاج → فرع/عزل Hotfix → RC → الإنتاج | Develop/Expansion → إكمال كل مكوّنات المرحلة → TEST كمرحلة متكاملة → QA/UAT/Regression → الإنتاج |

- كل Hotfix إنتاجيّ **يجب** أن يُدمَج أماميًّا في خطّ التوسّعة.
- **يُمنع** تحويل TEST إلى بيئة إصدار للإصلاحات اليومية.
- **يُمنع** خلط ملفات/Migrations/Builds المسارين دون توثيق واضح.

### 4.6 — انتقال التوسّعة إلى الإنتاج (Expansion → Production)
عند اكتمال التوسّعة على TEST **لا** تذهب إلى RC. التسلسل:
اكتمال التطوير → تجميع المرحلة على TEST → اختبارات تقنية شاملة → UAT التوسّعة على TEST → إصلاح الملاحظات → Regression نهائيّ على نسخة TEST المثبّتة → **مطابقة كل Hotfixes المنشورة على الإنتاج** → اعتماد Go-Live → Backup + خطة Rollback → النشر إلى الإنتاج `reports` → Hypercare.

- **إلزاميّ:** إنشاء **Release Manifest** نهائيّ يُثبِت أن النسخة المُرحَّلة للإنتاج = نسخة TEST المعتمَدة (يختلفان فقط في إعدادات البيئة).

### 4.7 — بوّابة مطابقة الـHotfixes قبل إطلاق التوسّعة (Hotfix Forward-Integration Gate)
- **إلزاميّ** قبل إطلاق التوسّعة: مقارنة بين الـHotfixes المنشورة على الإنتاج منذ بدء تطوير المرحلة، وكود التوسّعة على TEST، واختبارات كل Hotfix.
- **أيّ Hotfix إنتاجيّ غائب عن التوسّعة = معوّق إطلاق (Launch Blocker).**
- **إلزاميّ:** تسجيل ذلك في `HOTFIX_FORWARD_INTEGRATION_REGISTER.md` (رقم الـHotfix، تاريخ نشر الإنتاج، الملفات المتأثّرة، نسخة/Commit الإنتاج، دليل الدمج في خطّ التوسّعة، الاختبارات المرتبطة، أول Build توسّعة يحتويه، نتيجة التحقّق على TEST عند نشر المرحلة الكاملة).

### 4.8 — تصحيح افتراضات سابقة (Prior-Assumption Correction)
- **مراجعة كامل حزمة التخطيط والوثائق التشغيلية لم تجد أي نصّ يفترض صراحةً أن التوسّعة تنتقل من TEST إلى RC.** وثيقة `RC-Environment-Full-Clone-Execution-Plan.md` تنصّ أصلًا على القاعدة الصحيحة (RC = بيئة Hotfix/Release الوحيدة، TEST تبقى لتطوير المنصّة الجديدة).
- الفجوة الوحيدة كانت **غياب سياسة رسمية مقنّنة** في `MASTER_EXECUTION_PLAN.md`/`ARCHITECTURAL_DECISION_REGISTER.md`/`TRACEABILITY_MATRIX.md`؛ وهذا القسم + AD-114 يسدّانها.
- **تأكيد صريح:** التوسّعة الكبرى **لا** تمرّ عبر RC؛ إطلاقها يكون من نسخة TEST المعتمَدة إلى الإنتاج مباشرة.
