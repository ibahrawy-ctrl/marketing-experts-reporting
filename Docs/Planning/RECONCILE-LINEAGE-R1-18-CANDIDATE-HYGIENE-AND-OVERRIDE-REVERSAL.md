## 4) المراجعة الأمنيّة النهائيّة (I.4)

### 4.1 `RoleCapabilities.cs` — سطر واحد

```
new("system", "positions.manage", "إدارة المناصب المرنة", AdminOnly)
```

`AdminOnly` هو أضيق نطاق ممكن. **صفر** قدرة جديدة لـHR أو Finance أو TeamLeader أو CeoSupport.

### 4.2 `ScopeResolver.cs` — اتّحاد نطاقات المناصب

| بند المراجعة (§4.4) | النتيجة | الدليل |
|---|---|---|
| توسّع رؤية أفقيّ بلا مبرّر | **لا** | الاتّحاد مشروط بمنصب **مُفعَّل** (`p.IsActive`) يحمل صلاحيّة رؤية، وهو ميزة إنتاجيّة حيّة تُستعاد لا تُخترع |
| منح دور جديد صلاحيّات إدارة | **لا** | `PositionPermissions.Allowed` قائمة **مغلقة** بمفتاحَي رؤية فقط، و`IsValid` يرفض ما عداها عند الإدراج |
| كسر 404 لمنع التعداد | **لا** | التعديل يوسّع مجموعة مُعرِّفات المستخدمين فقط؛ لا يمسّ مسار قرار 404/403 |
| تحويل منع المورد إلى كشف وجوده | **لا** | لا تغيير في أيّ `Result`/`StatusCode` |
| رؤية HR/Finance خارج النطاق | **لا** | لا إسناد مناصب افتراضيّ لأيّ دور؛ الإسناد إداريّ صريح |
| كسر سلوك CPW-R2/R3 المعتمد في UAT | **لا** | `RoleMatrixCapabilitiesTests` و`ScopeEnforcementTests` خضراء ضمن 1993 |

**الدليل الحاسم على استحالة تصعيد الامتياز:** حتّى لو أُسنِد لمستخدم منصب بنطاق `AllCompany`،
فإنّ أقصى ما يناله هو **الرؤية**؛ الاعتماد يبقى محكومًا بـ`CurrentApproverId` وحده، ولا يوجد في
`PositionPermissions.Allowed` مفتاح اعتماد أو كتابة أصلًا فلا يمكن إسناده.

**ملاحظة اتّساق:** فرعا `Department`/`Team` لا يُصفّيان `IsActive` بينما `AllCompany` يُصفّيه —
وهذا **مطابق حرفيًّا** لسلوك مسار الدور الملتزَم أصلًا (`team`/`department` بلا تصفية،
`company/governance` بتصفية). لا تعارض جديدًا يُدخَل.

**الحكم:** `Security Scope Expansion = 0` — لا تعديل مطلوب.
