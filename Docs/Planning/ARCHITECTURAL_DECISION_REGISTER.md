# ARCHITECTURAL_DECISION_REGISTER

### سجلّ القرارات المعمارية المُوحَّد — ADRs الموثّقة + القرارات المقترحة من المراجعة المُصادَق عليها

> **الغرض:** مرجع واحد لكل قرار معماريّ يحكم التنفيذ اللاحق، يجمع القرارات الموثّقة في BRD (ADR-001..012) والقرارات الجديدة المقترحة من التدقيق (AD-101..113).
>
> **الحالات:** `Accepted` مُعتمَد · `Proposed` مقترح · `Deferred` مؤجّل · `Superseded` مُستبدَل · `Requires Owner Decision` يحتاج قرار مالك.
>
> **قاعدة:** التوصيات مُعلَّمة كتوصيات؛ القرارات المؤجّلة تبقى مؤجّلة؛ لا تُتَّخذ قرارات عمل نيابةً عن المالك. مصدر الأدلّة: BRD Ch14 + المستودع (`develop`) + `ENTERPRISE_ARCHITECTURE_REVIEW_VALIDATION.md`.

## الجزء ب — قرارات جديدة مقترحة من المراجعة المُصادَق عليها

> هذه قرارات **Proposed / Requires Owner Decision** — لم تُعتمَد بعد. مُعلَّمة صراحةً كتوصيات.

### AD-101 — حدود Modular Monolith
- **الحالة:** Proposed
- **السياق:** ADR-001 يفرض monolith، لكن حدود الوحدات غير مفروضة آليًّا (لا يمنع اعتماد وحدة على تفاصيل أخرى).
- **القرار (توصية):** تعريف حدود الوحدات صراحةً (Clients/Reports/Kpi/Governance/Employee/Notifications) مع قاعدة «لا اعتماد أفقيّ مباشر إلا عبر عقود Application». اختبار معماريّ اختياري لاحقًا.
- **البدائل:** ترك الحدود ضمنية (خطر تشابك) · فرضها باختبار ArchUnit الآن (overengineering مبكّر).
- **العواقب:** يحافظ على قابلية التطوّر لاحقًا إلى نواة سير عمل مشتركة؛ تكلفة توثيق منخفضة.
- **النطاق:** كل المنصّة · **المرحلة:** P0 (توثيق)/مستمرّ · **الدليل:** بنية 4 طبقات · **المالك:** المعماري.

### AD-102 — نواة سير العمل الخفيفة (Lightweight Workflow Core)
- **الحالة:** Requires Owner Decision (توصية قوية: Option B)
- **السياق:** مسارات الاعتماد صلبة مكرّرة عبر `SubmissionService`/`LeaveRequestService`/`GovernanceEscalationService` (grep على محرّك = 0). ADR-004 يفرض محرّكًا مركزيًّا.
- **القرار (توصية):** بناء **نواة خفيفة مشتركة (Option B)** عند بلوغ **P3** فقط، تدعم: تعريف سير العمل، الإصدار، مراحل مرتّبة، انتقالات مسموحة، حلّ الفاعل (Actor Resolution)، اعتماد/رفض، تعليقات، خطّ زمنيّ للتدقيق، طوابع SLA، خطّافات إشعار، إجراءات idempotent. **قابلة للتوسّع** لكن تُنفَّذ حالات الاستخدام الحالية والمعتمَدة فقط أولًا.
- **البدائل:** Option A إبقاء السلاسل الصلبة (دَين متراكم) · Option C محرّك BPMN كامل الآن (**overengineering مرفوض**).
- **العواقب:** يزيل تكرار منطق الاعتماد بمصدر واحد؛ لا يعطّل P0/P1؛ يتطوّر لاحقًا إلى C عند ظهور حاجة تهيئة ديناميكية حقيقية (CRM/تنفيذ متعدد المسارات).
- **النطاق:** كل مسارات الاعتماد · **المرحلة:** P3 (لا قبله) · **الدليل:** القسم 6 من تقرير التدقيق · **المالك:** المعماري + مالك المنتج.

### AD-103 — توحيد Permission Service
- **الحالة:** Deferred (توصية: تأجيل مع تغطية اختبار صارمة الآن)
- **السياق:** حرّاس التخويل موزّعة عبر الخدمات (دَين مُسمّى Ch14.14)؛ `ScopeResolver` موحّد للنطاق لكن قرارات التخويل موزّعة.
- **القرار (توصية):** **تأجيل التوحيد** إلى ما بعد استقرار المجالات، مع **تعزيز تغطية اختبار النطاق (Scope) الآن** كتخفيف لمخاطرة تسريب النطاق (R6).
- **البدائل:** توحيد فوريّ (يزاحم P0/P1 بلا حاجة فورية).
- **العواقب:** يبقي سطح الخطأ الأمني مضبوطًا باختبارات دون مشروع إعادة هيكلة كبير مبكّر.
- **النطاق:** التخويل · **المرحلة:** اختبار في P0، توحيد مستقبليّ · **الدليل:** انتشار الحرّاس + Ch14.14 · **المالك:** المعماري + مالك الأمن.

### AD-104 — Reporting Read Models
- **الحالة:** Deferred (توصية مستقبلية)
- **السياق:** التقارير/التجميع تعمل على OLTP مباشرةً (لا Read Models)؛ دَين مُسمّى Ch14.14.
- **القرار (توصية):** إدخال Read Models/Materialized Views **عند التوسّع** (P8)، لا قبل ظهور ضغط أداء فعليّ.
- **البدائل:** بناء Read Models الآن (تحسين سابق لأوانه).
- **العواقب:** يحافظ على البساطة الآن؛ يمهّد لذكاء التقارير لاحقًا.
- **النطاق:** التقارير/BI · **المرحلة:** P8 · **الدليل:** لا Read Model في الخدمات · **المالك:** المعماري + مالك التقارير.

### AD-105 — Metrics Catalog
- **الحالة:** Proposed (رؤية P8)
- **السياق:** BRD Ch10.4 يفرض Version/Owner للمقاييس لكن لا يحدّد التخزين (CL-13).
- **القرار (توصية):** جدول كتالوج مقاييس مخصّص (Metric + MetricVersion + Owner + Definition) عند بناء BI.
- **البدائل:** تعريف المقاييس في الكود/التهيئة (يفقد الحوكمة والإصدار).
- **العواقب:** أساس موحّد للتقارير القابلة للحوكمة.
- **النطاق:** BI · **المرحلة:** P8 · **الدليل:** BRD Ch10 · **المالك:** المعماري + مالك التقارير.

### AD-106 — File Service
- **الحالة:** Deferred (رؤية P4، مرتبط بـ ADR-011 + CL-04)
- **السياق:** تخزين ملفات محليّ فقط؛ لا تصنيف/إصدار/تصدير مُدقَّق. دَين مُسمّى Ch14.14 (local files → Object Storage).
- **القرار (توصية):** File Service مُصنَّف + مُصدَّر إصدارًا مع قاعدة تجاوز التصنيف المحسومة في CL-04، عند P4. تخزين محليّ يبقى ما لم يُعتمَد Object Storage صراحةً.
- **البدائل:** إبقاء التخزين البسيط (يفشل مع حوكمة الملفات).
- **العواقب:** أمن بيانات + أثر تدقيق للملفات.
- **النطاق:** File Service · **المرحلة:** P4 · **الدليل:** ADR-011 · **المالك:** مالك الأمن + مالك المنتج.

### AD-107 — Event/Outbox Architecture
- **الحالة:** Accepted جزئيًّا (Email Outbox) + Proposed (Event Bus داخليّ)
- **السياق:** Outbox للبريد **مُطبَّق** (`EmailOutboxDispatcher`). لا Event Bus داخليّ عامّ للأحداث بين الوحدات.
- **القرار (توصية):** إبقاء Outbox للبريد؛ تقييم Event Bus داخليّ خفيف **عند** بناء نواة سير العمل (P3) لربط إجراءات سير العمل بالإشعارات/التدقيق بشكل idempotent.
- **البدائل:** استدعاءات مباشرة بين الخدمات (تشابك).
- **العواقب:** فكّ ارتباط + موثوقية؛ لا يُبنى قبل الحاجة (P3).
- **النطاق:** الأحداث/الإشعارات · **المرحلة:** Outbox مُطبَّق / Event Bus في P3 · **الدليل:** المستودع · **المالك:** المعماري.

### AD-108 — النطاق الحالي مقابل نطاق CRM المستقبليّ
- **الحالة:** Accepted (فصل صريح)
- **السياق:** النطاق الحالي = تقارير/موظف/حوكمة أساسية/عملاء/مشاريع/مبيعات. CRM B2B (Lead→Contract) = رؤية P6 غائبة (grep=0).
- **القرار:** **عدم خلط CRM في الـ backlog الحالي.** يبقى P6، ومشروط بحسم CL-02 (Client/Company).
- **البدائل:** بدء CRM مبكّرًا (يزاحم الأولويات المعتمَدة بلا مبرّر).
- **العواقب:** حماية الأولويات المعتمَدة.
- **النطاق:** CRM · **المرحلة:** P6 · **الدليل:** grep=0 + BRD P6 · **المالك:** مالك المنتج.

### AD-109 — عزل قاعدة الاختبار (Test DB Isolation)
- **الحالة:** Proposed (توصية)
- **السياق:** اختبارات التكامل تستخدم قاعدة PostgreSQL **دائمة مشتركة** (`reporting_test`) ⇒ تراكم بيانات + تصادم هجرات محتمل (R8).
- **القرار (توصية):** الانتقال إلى قاعدة **عابرة لكل تشغيل** (respawn/schema-per-run) أو Testcontainers محليّ للتطوير، مع الإبقاء على قاعدة النشر (لا Testcontainers في الإنتاج).
- **البدائل:** إبقاء القاعدة المشتركة مع حلول يدوية موثّقة (هشّ).
- **العواقب:** نتائج اختبار موثوقة قابلة للتكرار.
- **النطاق:** الاختبارات · **المرحلة:** P0 · **الدليل:** نمط pitfalls الموثّق · **المالك:** المعماري.

### AD-110 — استراتيجية التحقّق الإنتاجيّ (Production Verification)
- **الحالة:** Proposed (توصية إلزامية قبل أي نشر)
- **السياق:** `develop` ≠ الإنتاج؛ حالة الإنتاج غير قابلة للاشتقاق من المستودع. النشر تاريخيًّا من نسخ معزولة في `/tmp`.
- **القرار (توصية):** قبل أي نشر: (1) التحقّق من سلسلة الهجرات على الخادم؛ (2) عزل الميزة في نسخة release مطابقة لأساس الإنتاج؛ (3) Backup (DB + publish + dist)؛ (4) Smoke قراءة-فقط؛ (5) إثبات Rollback. توثيق كل ذلك.
- **البدائل:** النشر مباشرة من `develop` (خطر انجراف الهجرات).
- **العواقب:** نشر آمن قابل للعكس.
- **النطاق:** العمليات/النشر · **المرحلة:** كل نشر · **الدليل:** دليل انجراف FlexiblePositions · **المالك:** العمليات + المعماري.

### AD-111 — API Versioning
- **الحالة:** Proposed (توصية)
- **السياق:** كل النقاط تحت `/api/*` بلا إصدار.
- **القرار (توصية):** تبنّي `/api/v1` عند أول تغيير كاسر متوقّع (لا الآن قسرًا).
- **البدائل:** لا إصدار (خطر كسر عملاء لاحقًا).
- **العواقب:** توافق خلفيّ مُدار.
- **النطاق:** الـ API · **المرحلة:** عند أول تغيير كاسر · **الدليل:** بنية المسارات · **المالك:** المعماري.

### AD-112 — Observability
- **الحالة:** Proposed (توصية)
- **السياق:** التدقيق (`AuditLog`) مُطبَّق، لكن لا توجد إشارة على tracing/metrics/structured logging مركزيّ.
- **القرار (توصية):** إدخال logging مُهيكل + صحّة/مقاييس أساسية (يوجد `/health`) تدريجيًّا؛ لا منصّة مراقبة ثقيلة الآن.
- **البدائل:** بلا observability (صعوبة تشخيص الإنتاج).
- **العواقب:** تشخيص أسرع.
- **النطاق:** العمليات · **المرحلة:** تدريجيّ (P0+) · **الدليل:** وجود `/health` + `AuditService` · **المالك:** العمليات.

### AD-113 — Disaster Recovery (RTO/RPO)
- **الحالة:** Proposed (توصية)
- **السياق:** Backups عبر `pg_dump` موثّقة، لكن لا RTO/RPO معلن ولا تدريب استعادة (DR Drill).
- **القرار (توصية):** تعريف RTO/RPO + تدريب استعادة دوريّ.
- **البدائل:** الاعتماد على backups بلا اختبار استعادة (خطر).
- **العواقب:** ضمان استمرارية.
- **النطاق:** العمليات · **المرحلة:** تشغيليّ · **الدليل:** نمط backups · **المالك:** العمليات.

### AD-114 — سياسة البيئات والنشر: TEST=Staging للتوسّعة · RC=Hotfix (Two-Track Environments Policy)
- **الحالة:** **Accepted (قرار معماريّ وتشغيليّ رسميّ مُعتمَد من المالك)**
- **السياق:** بيئتان مستقلّتان (TEST على المنفذ 5091، RC مقترَح على 5092 — راجع `RC-Environment-Full-Clone-Execution-Plan.md`). كان نطاق كلٍّ منهما مُمارَسًا لكن **غير مُقنَّن رسميًّا** في حزمة التخطيط، ما يفتح خطر خلط المسارين (نشر Hotfix إلى TEST، أو تمرير التوسّعة عبر RC).
- **القرار:**
  1. **TEST = Staging للتوسّعة المؤسسية الكبرى فقط** — تُجمَّع كمرحلة متكاملة واحدة؛ ليست نسخة موازية لكل إصدار/Hotfix إنتاجيّ.
  2. **RC = بيئة Hotfix/الإصلاح السريع** المبنيّ على أساس الإنتاج الحالي.
  3. **التوسّعة الكبرى لا تمرّ عبر RC إطلاقًا**؛ إطلاقها من نسخة TEST المعتمَدة إلى الإنتاج مباشرة.
  4. **الـHotfixes لا تُنشَر فرديًّا إلى TEST**؛ لكن **يجب** دمجها أماميًّا (Forward-Merge) في كود التوسّعة، وظهورها ضمن التوسّعة الكاملة على TEST إلزاميّ عند نشر المرحلة.
  5. **UAT التوسّعة** على نسخة TEST مثبّتة (pinned)؛ **UAT الإصلاح السريع** على RC محصورًا بالسيناريو المتأثّر.
  6. **يُمنع خلط ملفات/Migrations/Builds المسارين دون توثيق واضح.**
  7. **إلزاميّ** إنشاء **Release Manifest** يُثبِت أن نسخة الإنتاج = نسخة TEST المعتمَدة (فرق الإعدادات فقط)، و**بوّابة مطابقة Hotfixes** عبر `HOTFIX_FORWARD_INTEGRATION_REGISTER.md` قبل الإطلاق (أيّ Hotfix إنتاجيّ غائب عن التوسّعة = Launch Blocker).
- **البدائل:** إبقاء النطاق ضمنيًّا (خطر خلط المسارين) · دمج البيئتين (يفقد عزل المسارين).
- **العواقب:** فصل صارم لخطّي الإصدار؛ حماية الإنتاج؛ منع تحوّل TEST إلى بيئة إصلاح يوميّ؛ ضمان احتواء التوسّعة على كل Hotfix قبل الإطلاق.
- **النطاق:** العمليات/النشر/التخطيط · **المرحلة:** ساري الآن ومستمرّ · **الدليل:** `MASTER_EXECUTION_PLAN.md` §تاسعًا (القسم 4) · `RC-Environment-Full-Clone-Execution-Plan.md` · `HOTFIX_FORWARD_INTEGRATION_REGISTER.md` · **المالك:** العمليات + المعماري + مالك المنتج.
- **علاقة بـ ADR-007/AD-110:** يوسّع ADR-007 (RC يطابق الإنتاج + بريد off) بتقنين **نطاق** RC، ويتكامل مع AD-110 (معيار التحقّق الإنتاجيّ) الذي يبقى مطبَّقًا على كل نشر في المسارين.

## خلاصة السجلّ

- **12 ADR موثّقة** في BRD (7 مُطبَّقة/مقبولة، 3 مؤجّلة رؤية، 1 معدّل النطاق، 1 مؤجّل صراحةً).
