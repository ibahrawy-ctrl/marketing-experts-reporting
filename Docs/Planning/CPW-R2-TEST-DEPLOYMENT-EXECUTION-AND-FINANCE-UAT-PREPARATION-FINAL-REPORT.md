## 7. المكتشفات

### 7.1 `CPWR2-DEF-01` — خطأ 500 على `PUT /api/clients/{clientId}/documents/{documentId}` — **مُشخَّص ولم يُصلَح**

**الخطورة:** متوسّطة (وظيفيّة) — **الأثر الأمنيّ: لا شيء.**

**السبب الجذريّ:** عند تعديل سياسة الرؤية يعيد `ApplyVisibilityAsync` بناء صفوف الأبناء (`ClientDocumentService.cs:685-719`)، لكنّ متتبّع التغييرات في EF Core يصنّف الصفّ الجديد **`Modified` بدل `Added`**، فيُصدِر `UPDATE` على مفتاح غير موجود بدل `INSERT`:

```
UPDATE client_document_allowed_roles SET "ClientDocumentId"=@p0,"CreatedAtUtc"=@p1,"RoleName"=@p2,"UpdatedAtUtc"=@p3
UPDATE client_document_allowed_users SET "ClientDocumentId"=@p6,"CreatedAtUtc"=@p7,"UpdatedAtUtc"=@p8,"UserId"=@p9
```

⟶ 0 صفّ متأثّر ⟶ `DbUpdateConcurrencyException` عند `ClientDocumentService.cs:338` ⟶ **500**.

**المصفوفة التجريبيّة (7 مسابر):**

| المسبار | العمليّة | النتيجة |
|---|---|---|
| P1 | تعديل بيانات وصفيّة فقط (بلا `visibilityType`) | **200** |
| P2 | `ClientScoped ⟶ ManagementOnly` (لا يحتاج صفوف أبناء) | **200** |
| P3 | `CustomUsers` مع صفّ قائم | **500** |
| P4 | `CustomUsers ⟶ ClientScoped` (حذف فقط) | **200** |
| P5a | `CustomRoles` كـ **Admin** مع صفّ قائم | **500** |
| P5b | `CustomRoles ⟶ ClientScoped` كـ Admin (حذف فقط) | **200** |
| P6 | مستند بلا صفوف ⟶ `CustomRoles` (**إضافة فقط**) | **500** |
| P7 | القراءة بعد الفشل | **200** (سليم) |

**الاستنتاجات:** مسار الحذف سليم؛ الفشل محصور في **إدراج** صفوف `client_document_allowed_roles` / `client_document_allowed_users`. يقع مع **Admin ومدير العميل معًا** ⟹ ليس مشكلة تفويض. محصور في `UpdateAsync` (PUT) وحده — **الإنشاء (POST) بسياسة `CustomRoles`/`CustomUsers` يعمل بشكل صحيح.**

**الأثر العمليّ:** لا يمكن **تغيير** سياسة مستند إلى `CustomRoles`/`CustomUsers` بعد إنشائه عبر مسار التحرير؛ الالتفاف = ضبط السياسة وقت الرفع.
**الأثر الأمنيّ = صفر:** النداء يفشل مغلقًا، والمعاملة تتراجع ذرّيًّا، ولا توسيع للرؤية. أُثبِت بلا فساد بيانات: بعد كلّ المسابر بقي صفّ صلاحيّة واحد فقط أُنشئ وقت الرفع لا عبر PUT.

**الحالة:** لم يُصلَح — التوجيه يمنع إصلاح العيوب صراحةً. يُسجَّل تذكرة مستقلّة.

### 7.3 إفصاحات إجرائيّة

1. **إعادة تصنيف إخفاق §12:** ما ظهر أوّلًا كـ«تسريب `allowedUserIds` إلى مدير العميل» هو **خلل في تصميم الاختبار لا عيب في المنتج**: `CanManageVisibilityAsync` = `AuthorizeWriteAsync(...) is null`، وهي تُرجِع `null` حين `client.AccountManagerId == uid` ⟹ مدير العميل هو بالتصميم مديرُ مستندات عميله. أُعيد الإثبات بفاعل سلبيّ صحيح: `finance/C ⟶ canManage=false, allowedRoles=null, allowedUserIds=null`.
2. **تدوير كلمة مرور مدير العميل:** كان `account.manager@uat.local` يُرجِع 401 لقِدَم السرّ المخزَّن؛ أُعيد ضبطه عبر المسار الرسميّ `POST /api/directory/users/{id}/reset-password` (200)، والسرّ الجديد في `/root/uat-prep-runtime/cpwr2-am.env` (600) ولم يُطبَع.
3. **زلّة خصوصيّة (مُفصَح عنها):** أمر عرض سابق طبع ثلاث كلمات مرور لحسابات UAT على **TEST فقط** (`UAT_PW_CEO` / `UAT_PW_GM` / `UAT_PW_OPS_MGR`) خلافًا لقاعدة «لا تطبع كلمة المرور». لا يخصّ الإنتاج ولا أيّ سرّ إنتاجيّ. **التوصية:** تدوير هذه الثلاثة قبل جولة UAT الرسميّة.
